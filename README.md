# AI Voice Interview

> 이 저장소는 개인용 [ai_interview](https://github.com/gumwoo/ai_interview)를 일반 취업 준비생용 서비스로 바꾸는 작업 저장소입니다. 지금 코드는 개인용 앱과 같고, 함께 설치하고 실행할 수 있게 앱 ID와 서버 포트(18090)만 다릅니다. 아래 설명은 개인용 앱 기준입니다.

평일 아침 전화처럼 울리는 알림을 받으면, AI가 음성으로 기술 면접을 진행하는 개인용 Android 앱입니다. 질문은 제가 만든 프로젝트 [FlowTicket](https://github.com/gumwoo/first_come-first_served)의 설계 기록과 장애 기록에서 나옵니다.

폴드에서 말로 면접을 끝까지 진행하고, 틀렸거나 일부만 맞힌 내용은 다음 면접에서 다시 묻습니다.

![폴드를 펼친 화면](docs/images/unfolded.png)

## 왜 만들었나요

설계 문서를 쓰고 코드를 설명할 수 있다고 생각해도, 막상 말로 하면 막히는 경우가 많습니다. 왜 그 방식을 골랐는지, 다른 방법은 왜 버렸는지를 입으로 설명하는 일은 눈으로 복습해서는 잘 늘지 않습니다.

혼자 연습하면 세 가지가 어렵습니다. 매일 같은 시간에 시작하기 어렵고, 내 답에서 무엇이 빠졌는지 알기 어렵고, 틀린 내용을 나중에 다시 말해 보지 않게 됩니다. 이 앱은 이 세 가지를 해결합니다.

## 어떻게 동작하나요

평일 오전 7시 30분이 되면 폰에서 알림이 울립니다. 받기를 누르면 AI가 질문을 하나 읽어 주고, 제가 말로 답하면 음성 인식 결과가 PC 서버로 갑니다. Claude가 답을 채점한 뒤 다음 질문이나 해설을 돌려주면 폰이 읽어 줍니다. 이렇게 15분쯤 진행합니다.

아래 면접관의 말은 채점 평가에서 Claude Sonnet이 실제로 낸 응답이고, 답변은 평가용 예시입니다.

> **면접관:** FlowTicket에서 같은 좌석을 여러 사람이 동시에 잡으려 할 때 초과판매를 어디에서 어떤 방식으로 막았는지 설명해 주세요. 검토했던 다른 방법들은 왜 고르지 않았나요?
>
> **나:** DB 조건부 업데이트로 막았습니다. AVAILABLE인 좌석만 HELD로 바꾸고 영향받은 행 수를 확인해서 다르면 롤백합니다. 다른 방법은 깊게 비교하지는 않았던 것 같습니다.
>
> **면접관:** 초과판매를 막는 위치와 방식은 정확하게 설명해 주셨습니다. 조건부 UPDATE 후 영향 행 수를 확인하고, 다르면 롤백하는 흐름도 맞습니다. 다만 검토했던 다른 방법을 왜 고르지 않았는지는 답변에서 다뤄지지 않았습니다. 조건부 UPDATE 대신 사용할 수 있었던 대안으로 JVM 락, Redis 분산락, 비관락, 낙관락 중 두세 가지를 골라, 각각 이 문제에서 어떤 한계가 있는지 설명해 주시겠어요?

정답과 오답만 가르지 않습니다. 일부만 맞으면 빠진 부분을 다시 묻고, 모른다고 하면 설명한 뒤 이해했는지 확인합니다. 음성 인식이 불확실하면 채점하지 않고 되묻습니다.

지난 면접은 통화 기록에서 다시 볼 수 있습니다. 복습으로 다시 나온 질문은 따로 표시되고, 맞히면 "이번엔 맞음"으로 남습니다.

## 설계하면서 정한 것들

### 전화처럼 보이지만 전화가 아닙니다

실제로 전화를 걸려면 전화번호 임대와 발신 요금이 필요한데, 혼자 쓰는 학습 앱에는 맞지 않습니다. 그래서 앱 안에 수신 화면을 만들었고, 대화는 데이터 통신으로 합니다.

잠금 화면에는 전화 전용 화면만 띄웁니다. 전화가 끝나면 닫히므로 홈과 설정은 잠금 위에 보이지 않습니다.

### 알람은 서버가 아니라 폰이 울립니다

서버에서 푸시를 보내면 PC에 문제가 있을 때 알림도 함께 사라집니다. 폰에서 `AlarmManager`로 예약하면 서버가 꺼져 있어도 알림은 울리고, 받은 뒤에 연결 실패를 알려 줄 수 있습니다. 같은 이유로 스케줄의 원본은 앱 하나로 두고, 서버에는 저장하지 않습니다.

### 끼어들기 대신 턴제로 만들었습니다

사람과 통화하듯 말을 끊고 끼어드는 대화는 자연스럽지만, 이 앱에서 풀 문제는 아닙니다. Android `SpeechRecognizer`는 계속 켜 두는 용도가 아니어서, 질문을 다 읽은 뒤 한 번씩 인식을 시작합니다. WebRTC나 별도 음성 API가 필요 없고, 인식 결과를 제출 전에 고칠 수도 있습니다.

### Claude 호출은 트랜잭션 밖에서 합니다

모바일 환경에서는 응답을 받기 전에 연결이 끊겨 같은 답변을 다시 보내는 일이 생깁니다. 그때마다 Claude를 호출하면 크레딧을 낭비하고 채점도 두 번 저장됩니다. 그래서 답변을 먼저 저장해 커밋한 뒤 트랜잭션 밖에서 Claude를 호출하고, 앱이 만든 요청 ID로 재전송을 구분합니다. 외부 API를 기다리는 동안 DB 커넥션을 쥐고 있지 않게 하는 효과도 있습니다.

### 채점은 믿기 전에 평가합니다

이 앱에서 가장 어려운 문제는 통화 화면이 아니라 채점 품질입니다. 틀린 해설을 음성으로 듣고 넘어가면 잘못 외우게 됩니다. 그래서 음성과 알람보다 텍스트 면접을 먼저 만들고, 프로젝트 문서와 코드로 대조한 답변 예시 32건과 AI의 판정을 비교했습니다. 일치율 기준을 넘긴 뒤에 앱을 만들었습니다. 모델이 함께 내놓는 확신도 값은 자기 평가일 뿐이므로 정확도의 근거로 쓰지 않습니다.

처음에는 비용이 낮은 Claude Haiku로 끝까지 가고 마지막에 Claude Sonnet으로 바꿀 계획이었습니다. 하지만 평가 기준을 실행 전에 정해 두고 측정해 보니, Haiku는 프롬프트를 세 번 고쳐도 확인용 일치율이 67~75%에 머물러 기준인 80%를 넘지 못했습니다. 같은 평가셋에서 Sonnet은 92%가 나와서, 계획을 바꿔 Sonnet을 기본 모델로 정했습니다. 다만 확인용 예시는 12건이고 측정도 한 번이라, 이 수치는 모델 선택의 근거이지 품질 보증은 아닙니다.

### 질문은 저장해 두고 재사용합니다

매번 질문을 생성하면 비용이 들고, 나오는 질문을 미리 검토할 수도 없습니다. 프로젝트 문서와 코드로 대조한 시드 질문을 먼저 쓰고, 후보가 없을 때만 생성해서 저장합니다. 시드에는 근거 문서와 기준 커밋을 남기고, 생성한 질문은 검증되지 않은 것으로 구분합니다.

### 혼자 쓰니까 뺀 것들

사용자가 한 명이므로 다중 사용자, 역할 권한, 기기 페어링, Google Play 배포는 만들지 않았습니다. 서버는 Tailscale 안에만 두고 인증은 고정 토큰 하나로 합니다.

## 실행 방법

서버를 띄우려면 Docker가 필요합니다.

`infra/.env.example`을 `infra/.env`로 복사해 비밀번호, 32자 이상의 API 토큰, Claude API 키를 채운 뒤 서버를 띄웁니다.

```bash
docker compose -f infra/compose.yaml up -d --build
```

```bash
curl http://localhost:18090/api/v1/health
```

환경 변수 `SPRING_PROFILES_ACTIVE=dev`를 주고 띄우면 `http://localhost:18090/dev/console`에서 브라우저로 면접을 시험할 수 있습니다.

테스트는 Testcontainers로 실제 PostgreSQL을 띄워 실행합니다.

```bash
cd backend && ./gradlew test
```

앱은 `android/`에 있고, Android SDK 37이 필요합니다. 설치한 뒤 설정 화면에서 서버 주소와 API 토큰을 입력합니다. 토큰은 APK에 넣지 않고 기기의 Android Keystore로 암호화해 보관합니다.

```bash
cd android && ./gradlew testDebugUnitTest installDebug
```
